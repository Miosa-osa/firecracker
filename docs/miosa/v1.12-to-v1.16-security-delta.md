# v1.12.0 → v1.16.1 security & correctness delta

Mined from the upstream Firecracker CHANGELOG (v1.16.1) on 2026-07-19, filtered to what materially affects MIOSA. This is the evidence behind treating the VMM upgrade (`miosa-v1.16`) as a real fix, not just version hygiene. Production runs stock v1.12.0.

## Data-corruption / snapshot-correctness fixes we are currently missing

| Fix (upstream, in the 1.13→1.16 range) | Why it matters to MIOSA |
|---|---|
| **Diff-snapshot memory-file corruption bug fixed** — Firecracker could corrupt the memory files of differential snapshots | We don't use diff snapshots today, but the fast-boot/generation program is exactly where they'd be adopted for incremental capture. Landing on a VMM without this fix would reintroduce a corruption class we just spent weeks killing at the platform layer. |
| **Block-device iovec data-corruption fix** — an error on an iovec other than the first caused a data-corruption issue | Direct block-path correctness. Given our history of guest-disk corruption, any VMM-level block fix is worth having. |
| **Full KVM custom MSR-range serialization** (`0x4b564d00–0x4b564dff`) — previously MSRs like `MSR_KVM_ASYNC_PF_INT`/`_ACK` were dropped from snapshots | Restored guests on v1.12 silently lose some paravirt MSR state. Correctness of every snapshot restore. |
| **`kvm-clock` monotonic-clock jump on restore fixed** — clock jumped by wall-time elapsed since snapshot; opt back in via new `clock_realtime` flag | This IS our measured multi-day resume clock-skew. The fix is default-correct in v1.16. |
| **`KVM_KVMCLOCK_CTRL` ioctl before resume** | Companion clock-correctness fix on the resume path. |

## Hardening additions

| Addition | Use for MIOSA |
|---|---|
| **virtio-rng per-request entropy capped to 64 KiB** | Bounds a guest entropy-request DoS. We attach virtio-rng today with no such bound on v1.12. |
| **VMGenID HID alignment fix** (avoids colliding with an upstream Linux VMGenID bug) | Prerequisite for the VMGenID snapshot-uniqueness gate (`production-hardening-gates.md` Gate 2). VMGenID is safer/more complete on v1.16. |
| **VMClock device** (uapi-group VMClock spec) | A second, cleaner clock-sync mechanism for clones — future option beyond the kvm-clock fix. |
| **Custom CPU template directly in the JSON config** | Makes Gate 1 (CPU template for cross-host/cross-stepping restore) materially easier to implement — the template can ride the machine config instead of a separate API dance. |
| **virtio `TRANSPORT_RESET` / `DEVICE_NEEDS_RESET` handling** | Correct device reset semantics; reduces a class of post-reset guest hangs. |

## Net

The upgrade carries **three independent data-corruption/correctness fixes** (diff-snapshot memory, block iovec, MSR serialization) plus the clock fix plus the CPU-template ergonomics that Gate 1 needs. It is the single highest-leverage VMM action and it is upstream-clean — no patch of our own required to get any of it.

## Jailer posture (checked against the live fleet 2026-07-19)

Our boot path already runs the jailer correctly: chroot per microVM, unprivileged uid/gid, capability drops, **cgroup v2**, **new PID namespace**, and `--netns`. That is a strong baseline and matches upstream production guidance.

**One gap:** the jailer is invoked **without `--resource-limit`**. Upstream supports `--resource-limit fsize=<n>` and `no-file=<n>` to cap the Firecracker process's file size and fd count. Setting these bounds the exact serial-device / stdout unbounded-output risk from `production-hardening-gates.md` Gate 3 at the jailer level (defense in depth alongside the `8250.nr_uarts=0` boot arg, which is the boot-path owner's change to make). Recommend adding `--resource-limit fsize=<cap> --resource-limit no-file=<cap>` to the jailer arg builder.
